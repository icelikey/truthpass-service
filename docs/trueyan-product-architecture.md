# 真验：白牌商品公共信誉服务架构（历史基线）

> 当前比赛 Demo 已切换为鱼油批次验收，详见 [fish-oil-development-plan.md](fish-oil-development-plan.md)。本文保留早期白牌 Type-C 方案，用于说明通用层边界。

## 1. 产品定义

**真验**不是一个完整电商商城，也不是一个只把商品信息写入区块链的溯源页面。

它是一层可以被其他 Agent 调用的可信服务基础设施：

> 用户的 Agent 提出购买目标，真验负责查找候选商品和服务，探测当前可用性，核验生产与交付证据，输出可解释的选择结果，并把本次结果沉淀为公共信誉。

用户自己的 Agent 负责理解“我要买什么”；真验负责回答“哪些商品和服务的证据值得相信”。

## 2. 第一品类：白牌 Type-C 充电线

首版选择白牌 Type-C 充电线，理由是：

- 白牌竞争充分，消费者通常关心性价比和实际质量；
- 指标容易结构化：导通、电阻、温升、充电电流、耐弯折、材料和批次；
- 可以同时展示原材料、生产、质检、出厂和物流节点；
- 可以模拟第三方检测 Agent 和平台控制的传感器 Agent；
- 不需要在首版承担食品、药品和化妆品的复杂责任边界。

比赛演示只使用模拟数据，不能把模拟传感器结果描述成真实硬件检测。

## 3. 一次购买的完整闭环

```text
用户 Agent
  ↓ 结构化任务：寻找一条合格、价格透明的 Type-C 充电线
真验 API / Skill
  ↓ 查询商品档案、供应商和检测服务
服务探测 Agent
  ↓ 健康检查、能力匹配、小型挑战任务
证据验收 Agent
  ↓ 比较批次、时间、签名、检测值和物流记录
真验评分器
  ↓ 质量、证据完整性、当前可用性、履约历史、价格透明度
商品证据卡
  ↓
链上公共信誉与验证记录
```

## 4. 系统分层

### 4.1 语义接入层

真验不重复建设通用语义层，提供结构化 API、Skill 或 MCP 适配器。

示例请求：

```json
{
  "category": "usb-c-cable",
  "requirements": {
    "maxPrice": 29,
    "minCurrentAmp": 5,
    "maxTemperatureRise": 25,
    "requiredEvidence": ["material", "qc", "outbound"]
  }
}
```

### 4.2 商品与证据登记层

使用关系数据库保存结构化事实，使用向量检索辅助商品描述召回，使用关系图表达：

```text
供应商 → 商品 → 批次 → 工序 → 质检 → 出厂 → 物流 → 售后
                    ↑       ↑       ↑
              传感器 Agent  第三方检测 Agent  人工抽检
```

向量数据库只用于“找相关商品和证据”，不能作为真实性判断的唯一来源。

### 4.3 服务注册与探测层

服务包括供应商、检测机构、物流和售后。每个服务登记：

- 服务身份和钱包地址；
- 能力清单；
- API 端点；
- 支持的输入输出格式；
- 当前健康状态；
- 历史履约记录。

真验先调用 `health`、`capabilities` 和 `probe`，再决定是否发送正式任务。

### 4.4 Agent 编排层

- `Planner Agent`：把购买目标转成验收标准；
- `Discovery Agent`：查找匹配的商品和服务；
- `Probe Agent`：探测当前可用性和能力；
- `Evidence Agent`：收集并标准化生产、检测、物流证据；
- `Verifier`：执行确定性规则；
- `Router Agent`：服务失败时切换候选；
- `Reputation Agent`：生成任务级反馈并写入公共信誉。

大模型负责规划和解释，关键的通过、拒绝和评分由规则引擎决定。

### 4.5 验收与评分层

首版评分建议：

```text
质量检测结果       30%
证据完整性与一致性 25%
当前服务可用性     15%
历史履约信誉       20%
价格和利润披露     10%
```

批次不匹配、签名失效和关键质检缺失属于关键失败，不能被平均分掩盖。

厂商利润先作为“厂商声明值”展示。真验可以验证价格计算和证据完整性，但不能声称仅凭链上数据就知道厂商真实成本或绝对合理利润。

### 4.6 链上公共信誉层

链上保存：

- 服务和商品身份；
- 批次 ID；
- 证据哈希；
- 验收结论和评分；
- 反馈来源；
- 时间戳；
- 撤销状态。

链下保存完整报告、原始传感器数据、图片、商业隐私和个人信息。

最小合约接口：

```solidity
registerService(serviceId, metadataURI)
recordFeedback(serviceId, taskHash, evidenceHash, score, accepted)
revokeFeedback(feedbackId, reasonHash)
```

### 4.7 展示层

商品详情页不只显示一个总分，而是显示“证据卡”：

- 当前服务是否在线；
- 质量指标是否达标；
- 哪些节点有第三方证明；
- 哪些数据是厂商自报；
- 本次验收为何通过或拒绝；
- 对应的链上记录和证据哈希。

## 5. 防刷分设计

- 没有真实任务哈希不能反馈；
- 同一调用者对同一任务只能反馈一次；
- 反馈必须绑定服务身份、响应和证据哈希；
- 新反馈权重高于长期未更新的旧反馈；
- 发现证据冲突可以撤销反馈；
- 后续再增加第三方身份、质押和地址关系分析。

## 6. 比赛 MVP

```text
一个品类：白牌 Type-C 充电线
三个候选服务：两个检测服务、一个物流服务
三个证据节点：原材料、质检、出厂
一个异常：报告批次不一致或传感器记录中断
一个推荐：选择当前可用且验收通过的服务
一张证据卡：显示原因和链上哈希
一个后续 Agent：读取公共反馈并复用选择结果
```
