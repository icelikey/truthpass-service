# TruthPass 风险评估与安全边界

> 文档版本：v1.4.0
> 状态：与当前集成分支对齐的风险基线
> 最近修改：2026-10-15
> 基线分支：`codex/integrate-v1.4.0`
> 关联版本：`docs/integration-v1.4.0.md`

## 1. 结论

TruthPass 的主要风险发生在现实数据进入系统之前。区块链能够确认提交者、时间、哈希、事件顺序和责任交接，但不能单独证明工厂确实按记录生产、传感器未被替换、样品未被调包或检测报告真实有效。

当前 v1.4.0 已实现的是可演示的证据协议、确定性验收、消费者钱包交易准备、Agent/CLI 查询和 BOT Chain 交互边界。真实机构签名、设备签名、生产数据接入、多租户治理和普通非部署钱包的现场交易仍属于待验收或后续工作。

完整信任链为：

```text
主体身份
  → 数据来源
  → 设备或机构签名
  → 批次与样品绑定
  → 多来源交叉验证
  → 确定性规则验收
  → BOT Chain 锚定
  → Consumer Agent 解释
  → 质疑、复检和仲裁
```

## 2. 攻击面与控制

| 攻击面 | 典型方式 | 控制要求 | v1.4.0 状态 |
| --- | --- | --- | --- |
| 厂商伪造 | 上传完整但虚假的生产记录 | 第三方签名、多来源交叉验证、现场抽检 | 方案与演示，真实机构接入待做 |
| 传感器篡改 | 替换设备、修改采集程序或回拨时间 | 设备身份、公钥、签名、校准记录、序列连续性 | 模拟协议，设备签名待做 |
| 样品调包 | 正常样品送检，异常产品出厂 | 封签、二维码/RFID、批次和物流交接绑定 | 规则已定义，现场流程待做 |
| 报告重放 | 旧报告绑定新批次 | 批次、时间、有效期、撤销状态和 nonce 检查 | 确定性检查已具备，真实签名待做 |
| 批次错配 | 原料、检测和物流记录属于不同批次 | `batchId`、`sampleId`、`evidenceId` 贯穿全链路 | 演示数据已覆盖，真实适配器待做 |
| 同源多 Agent | 生产、检测和验证 Agent 由同一主体控制 | 显示来源主体，按独立性加权，不能把同源数据算多方证明 | 页面协议已定义，治理待做 |
| 女巫刷信誉 | 多钱包互相提交好评 | 反馈绑定真实任务和购买，一次性凭证，反刷和衰减 | 匿名凭证和一次性反馈已实现，公共信誉回流待做 |
| Agent 幻觉 | 把缺失证据解释为已通过 | Agent 只能规划、解释和路由；Verifier 产生最终状态 | v1.4.0 已明确边界 |
| Agent 越权 | 直接改数据库或调用结算 | 工具白名单、角色权限、签名交易、审计日志 | 部分实现，生产密钥隔离待做 |
| 单点仲裁 | 单个模型决定质疑结果和资金分配 | Verifier、第二 Agent 或仲裁钱包共同确认 | Audit Escrow 已部署，独立角色待做 |
| 隐私泄露 | 原始报告、商业机密和用户身份上链 | 原文链下，链上保存哈希、状态、版本和事件 | 协议已定义，生产存储治理待做 |
| Oracle 风险 | 链上无法直接观察现实生产 | 机构、设备、人工和多来源证据共同验证 | 当前仍为 demo/synthetic |

## 3. Agent 责任边界

- Production Agent：整理厂家、ERP、MES、设备和批次数据。
- Inspection Agent：组织质检任务、实验室报告和设备检测。
- Consumer Agent：查询、解释、推荐、购买和提出质疑。
- JEV：识别缺口、冲突、异常和下一步路径。
- Deterministic Verifier：检查批次、时间、签名、单位、方法和阈值。
- Audit Agent：复核质疑证据并提交 `agentRunHash`。
- Second Agent / Human Arbiter：复核高风险争议并触发最终仲裁。
- Relayer：只提交已经签名的交易，不修改证据内容。

必须保持：JEV 不直接决定通过；Agent 不修改质量事实；区块链不替代现实检测；钱包不替代质检员责任；资金结算不由单个模型决定。

## 4. 质疑和结算门禁

```text
消费者 Agent 发现异常
  → 用户钱包锁定质押
  → Audit Agent 提交 evidenceRoot、agentRunHash 和审计结果
  → Deterministic Verifier 验证规则
  → 第二 Agent 或仲裁钱包复核
  → BOT Chain 记录结论
  → 返还、奖励或扣除质押
```

没有 `agentRunHash`、`evidenceRoot`、`policyHash` 和 `verifierVersionHash`，不能结算质押。消费者钱包不能直接调用最终结算方法。

## 5. v1.4.0 交付状态

### 已实现或已验证

- 鱼油批次和确定性验收；
- Evidence Envelope 和哈希；
- Consumer Gateway 与 Audit Escrow 交易准备；
- JEV/TypeSafe 接口和 fallback 边界；
- CLI 查询、解释和订单准备；
- EIP-6963 钱包发现、Chain ID `677` 检查和真实 receipt 校验；
- CFI Manifest、公共标准、匿名凭证和一次性反馈协议；
- 本地 `typecheck`、测试和构建通过。

### 仅演示或待验收

- 内置批次、传感器和历史回放均为 `demo/synthetic`；
- 合约部署和角色授权证明链上基础设施存在，不等于真实生产业务已认证；
- 真实第三方机构、工厂、实验室、物流和设备签名尚未完整接入；
- ProductPolicy、凭证和反馈仍需持久化治理；
- 普通非部署钱包的 `purchase → contribution → openChallenge` 主网现场交易仍需回填真实 receipt。

## 6. v1.5 进入条件

v1.5 只能在以下条件满足后把“真实企业试点”列为进行中：

1. 至少一个真实批次完成端到端回放；
2. 至少一份真实第三方报告通过机构签名验证；
3. 生产、检测和物流证据能按批次关联；
4. 错批次、重复报告、证书撤销和缺失证据能够失败关闭；
5. 普通用户钱包交易能回读 receipt 和匹配业务事件；
6. 页面和文档持续区分 `demo/synthetic`、`anchor_pending` 和 `mainnet_receipt_verified`。
