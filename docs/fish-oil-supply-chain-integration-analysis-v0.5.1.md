# TruthPass 鱼油供应链接入与证据治理专题分析

> 文档版本：v0.5.1 专题补充  
> 状态：分析与实施建议，不代表已实现能力  
> 适用范围：鱼油批次从原料验收到交付的低改造接入、证据治理、Agent/JEV/确定性 Verifier 分工  
> 与现有审计关系：[architecture-audit-v0.5.1.md](architecture-audit-v0.5.1.md) 仍是当前仓库实现状态的依据；本文只补充厂家接入和生产级治理专题，不覆盖或改写既有审计结论。

## 0. 结论先行

TruthPass 应先做“读已有数据、形成可复核证据、暴露缺口”，再逐步走向智能工厂。最小改造路径是：

    已有系统/设备导出
        → 只读适配器与 Edge Gateway
        → EvidenceEnvelope 标准化
        → 批次图与样品/设备/交接绑定
        → JEV 做缺口识别和路由
        → 确定性 Verifier 做规则验收
        → 链下保存原文，BOT Chain 锚定最小承诺

三条边界必须保持：

1. Agent 可以帮消费者提出问题、选择证据范围和安排下一步，但不能把厂商自报改成第三方证明，也不能静默删除负面证据。
2. JEV 可以识别缺失、冲突和下一步路由，但不能覆盖 Verifier，也不能替代实验室仪器、校准体系或法规判断。
3. 链上只能证明某主体在某时提交了某个承诺，不能单独证明设备没有被替换、样品没有被调包或实验室一定独立。

建议采用 accepted、accepted_with_scope、review、rejected 四类结果。每类结果都要带声明范围、证据来源、缺失字段、冲突和未覆盖范围。

## 1. 三阶段接入路线

### 1.1 P0：比赛 Demo，零产线改造

目标是演示数据模型、证据关联、候选服务选择和规则回放，不宣称真实工厂已经接入。

数据可以来自：

- demo/synthetic 的批次主记录；
- 预先整理的实验室报告摘要；
- 模拟冷链温度事件；
- 模拟设备/实验室签名、序列号和错误批次；
- 一个正确服务、一个离线服务、一个错批次服务。

P0 不要求厂家安装网关、购买传感器或改造 MES。只需提供一套字段说明和样例数据，并明确每个字段是厂商自报、第三方报告、设备观察还是未覆盖。

P0 的演示验收：

- 可以把“查含量、新鲜度、冷链”转成固定任务；
- 可以展示候选服务的在线、离线、错批次和指标失败；
- 确定性规则可以重复得到相同结果；
- 页面明确显示 demo/synthetic、规则版本和未覆盖项目；
- 不把模拟签名、哈希或链上目标网络说成现实生产认证。

### 1.2 P1：低改造试点，读已有系统

目标是在一个产品、一个工厂或一条物流线路上验证真实数据闭环，原则是“旁路读取、批次对齐、失败可回放”，不向 PLC、MES 或 ERP 写控制指令。

推荐接入顺序：

1. LIMS/第三方实验室：先取得带报告编号、样品编号、检测方法、单位和签名的结果；
2. 温度记录器/WMS：取得 CSV、JSON、HTTPS 或 MQTT 导出；
3. ERP：取得物料批次、供应商批号、生产订单和出货批次；
4. MES：取得工艺步骤、工单、设备、操作者和时间；
5. TMS/物流：取得运单、承运商、交接、路线和温度摘要；
6. 设备导出：最后接入关键设备的批次、运行和报警记录。

P1 的 Edge Gateway 负责：

- 校验文件/API 格式和签名；
- 统一时区、单位、枚举和时间格式；
- 将外部批号映射到 TruthPass 的内部批次 ID；
- 绑定样品、设备、工单和交接关系；
- 生成事件序列、前一事件哈希和重复检测键；
- 原文入链下证据仓，摘要进入验证队列；
- 断网时本地缓存，恢复后按 requestId 幂等重放。

P1 的最低投入不是改造整条产线，而是确定三个治理约定：

- 批次、样品、设备的编号规则；
- 哪些系统是事实来源，哪些只是转录来源；
- 哪些字段公开、受限、只留哈希或暂不提供。

P1 不能以“接入成功”作为通过条件。试点门禁应是：至少一个真实批次完成端到端回放；同一报告不能无提示地绑定到两个批次；签名、时间回拨、重复事件和缺失字段有明确结果；断网恢复后不产生重复验收。

### 1.3 P2：智能工厂，事件化与闭环治理

目标是多工厂、多实验室、多物流服务的持续运行，不是一次性导入文件。

P2 需要补齐：

- ERP、MES、LIMS、WMS、TMS 和 IoT 平台的稳定连接器；
- 设备身份证书、密钥轮换、吊销、校准和维护记录；
- 生产批次、样品、容器、包装序列和物流单元的数字关系；
- 事件流、时间同步、离线缓冲、幂等重试和审计日志；
- 规则集、检测方法、标准版本和实验室资质的版本管理；
- 独立复检、申诉、冻结、撤销和争议仲裁；
- 数据保留、访问审批、删除/撤回请求和跨境边界；
- 运行指标：延迟、缺失率、签名失败率、批次错配率、重复率和复检率。

P2 可以将验证结果反馈给生产质量流程，例如提示补采样、隔离批次或触发复检，但 TruthPass 的规则结果不能直接变成设备控制命令。任何放行、召回、销毁或法规申报仍由有权限的质量负责人和法定流程确认。

## 2. 既有系统和数据的接入方式

| 来源 | 首次接入的最小字段 | 推荐方式 | 事实边界 |
| --- | --- | --- | --- |
| ERP | 供应商、原料批号、生产订单、成品批号、出货单 | 定时只读 API 或加密文件交换 | 说明“系统登记了什么”，不证明原料物理身份 |
| MES | 工单、工艺步骤、开始/结束时间、设备、操作者、异常 | 只读 API、事件订阅或批次导出 | 说明“生产系统记录了什么”，不等于每个传感器读数真实 |
| LIMS | 样品 ID、报告 ID、方法、单位、结果、判定、签发人、签发时间 | API、SFTP、签名 PDF/JSON | 适合做检测结果证据，实验室资质和方法适用性仍需核查 |
| 第三方实验室 | COA、谱图/原始数据索引、样品交接、检测方法、签名 | 签名 JSON + 原文 PDF/对象存储 | 报告证明实验室作出该报告，不自动证明采样链无瑕疵 |
| WMS/温度记录器 | 库位、入库/出库、设备 ID、时间序列、温度/湿度、报警 | CSV/JSON/MQTT/HTTPS | 说明设备观测；需补校准、安装位置和设备替换信息 |
| TMS/物流 | 运单、承运商、交接、路线、车辆/箱码、温度摘要、签收 | API、电子运单、设备导出 | 说明运输事件和交接，不替代货损或责任认定 |
| 设备/SCADA/PLC 导出 | 设备 ID、工艺批次、关键参数、报警、校准引用、时间序列 | 只读文件、OPC UA/MQTT 网关或厂商 API | 首期只采集和验证，禁止把导出记录直接当作独立第三方证据 |

接入适配器要保留三份关系：

    原始记录 → 规范化事件 → TruthPass 证据引用

规范化失败、字段被截断、单位无法转换、签名无法验证时，原始记录仍保留，事件状态应为 invalid、partial 或 review，不能被静默丢弃。

## 3. Agent、JEV 与确定性 Verifier 的分工

### 3.1 数据筛选和路由顺序

    消费者问题
      ↓
    Agent 将问题映射为 policy 与 requestedChecks
      ↓
    代码从授权范围内读取 EvidenceEnvelope 摘要
      ↓
    JEV 判断完整性、冲突、时效与下一步路由
      ↓
    确定性 Verifier 按 policy 计算结果
      ↓
    Agent 只解释已确定结果，并列出缺口和下一步

Agent 的筛选条件必须来自代码生成的状态摘要，不允许模型自由拼接检测值。可筛选的是“哪些证据与本次问题有关、哪些服务有能力、哪些字段对当前受众可见”；不可筛选的是“只展示通过的证据”。

### 3.2 JEV 应输出什么

JEV 输出固定枚举和引用，而不是长篇判断：

- route_to_rule_verifier：所需字段存在、来源可回查、没有未处理冲突；
- request_more_evidence：缺少关键指标、样品关系或时间范围；
- route_to_recheck：批次冲突、签名异常、设备状态不稳定、模型超时或置信度不足；
- reject_evidence：格式、身份、重复或最低可信门槛失败。

JEV 的置信度只能影响路由和结果范围，不能把低置信度提升为通过。JEV 超时、模型版本未登记、输入哈希无法回放、输出过期或出现未知枚举时，必须进入 review 或 request_more_evidence。

### 3.3 Verifier 的确定性职责

Verifier 负责：

- 批次、样品、设备、工单和报告关系是否匹配；
- 时间顺序、有效期、序列连续性和重复事件；
- 签名、公钥、密钥状态和证据哈希；
- 数值单位、检测方法和规则版本是否一致；
- 指标阈值、冷链区间、缺失字段和硬失败条件；
- 证据范围、结果状态、原因代码和证据根。

当前 Demo 的 EPA+DHA 70%、过氧化值 5、TOTOX 20、冷链中断 6 小时只能作为演示 policy；生产 policy 必须绑定产品规格、适用标准、检测方法、单位、实验室资质和生效日期。

### 3.4 解释边界

Agent 的解释只能改写 VerificationResult：

- 可以说“按本次声明范围，EPA+DHA 和氧化指标通过”；
- 可以说“重金属未覆盖，不能据此推断重金属安全”；
- 可以解释“报告批次不匹配，因此本次不接受”；
- 不能说“区块链证明产品绝对真实”；
- 不能说“JEV 已确认样品未被调包”；
- 不能把“没有记录”说成“没有发生”。

## 4. 最小披露与负面证据规则

最小披露保护商业和个人信息，但不能变成选择性营销。建议给每个字段维护五种状态：

- verified：有可回查来源，且满足当前规则；
- failed：有可回查来源，但不满足规则；
- missing：在声明的范围内应有，但当前没有提供；
- restricted：有记录，但当前受众无权查看；
- not_covered：本次 policy 没有检查该项目。

对外证据卡即使隐藏具体值，也必须显示状态和原因，例如：

    {
      "field": "heavy_metals",
      "status": "restricted",
      "sourceClass": "third-party-lab",
      "reasonCode": "AUDIENCE_SCOPE",
      "isUsedForDecision": false
    }

如果厂家拒绝提供报告，应生成一个带时间、主体和原因的 disclosure_event。若系统没有该字段，应显示 missing 或 not_covered，不能显示绿色空白。若存在失败记录和后续替代记录，两者都要保留，后者只能通过版本关系说明替代或复检。

最小披露的四层视图：

1. 消费者视图：结论、范围、关键指标状态、风险、缺口、证据来源类别；
2. 评委/审计视图：事件 ID、哈希、规则版本、时间线、JEV 路由和锚定状态；
3. 厂家视图：可见批次、待补字段、复检与争议处理；
4. 实验室/监管视图：完整报告、样品交接、方法、原始数据索引和资质材料。

权限只决定显示内容，不能改变底层证据账本和最终规则结果。

## 5. 鱼油全流程、指标和绑定关系

下表列出建议的生产级证据目录。具体阈值和法定项目应由产品类别、目标市场、标准、检测方法和实验室资质共同确定。

| 环节 | 关键检测/记录指标 | IoT/设备可采集项 | 适合第三方实验室验证 | 主要绑定关系 |
| --- | --- | --- | --- | --- |
| 1. 原料供应与验收 | 鱼种/部位、产地/捕捞区、供应商批号、感官、温度、初始 PV/AV、游离脂肪酸、水分、污染物风险 | 车辆/容器温度、GPS/时间、称重、收货门禁、容器码 | 重金属、二噁英/PCB、PAHs、脂肪酸谱、氧化指标、必要时微生物 | 供应商批号 → 原料批次 RM-* → 收货单 → 样品 S-* |
| 2. 取样与隔离 | 取样位置、样品量、封样、留样、抽样人、样品温度、隔离状态 | 条码/RFID、电子秤、冷库温度、封签/开封时间 | 见证取样、复测、样品同一性与污染物 | 原料批次 → 样品 → 封样/交接 → 实验室报告 |
| 3. 熔炼/预处理 | 温度、时间、杂质、水分、游离脂肪酸、收率、过滤压差 | 罐温、流量、压力、搅拌、阀门状态、设备报警 | 中间体脂肪酸/氧化指标、必要时污染物 | 原料批次 → 工单 → 设备运行段 → 中间体批次 |
| 4. 精炼（脱胶/中和/脱色/过滤） | 酸价/FFA、磷脂/胶质、色泽、皂脚残留、过滤完整性、氧化变化 | 温度、pH、真空、流量、压差、滤芯 ID、换滤记录 | FFA、磷、色泽、氧化指标、残留物/污染物 | 中间体批次 → 工艺步骤 → 设备/滤芯 → 中间体版本 |

| 7. 配方混合 | 各原料比例、EPA/DHA 目标、抗氧化剂、载体油、均匀性、过敏原/配方版本 | 计量、搅拌、罐温、液位、阀门、批次扫描 | 脂肪酸谱、均匀性、氧化指标、必要时微生物/过敏原 | 配方版本 → 投料记录 → 混合批次 → 样品 |

| 10. 成品放行 | EPA/DHA、PV/AV、p-AV/TOTOX、净含量、微生物/污染物、留样和放行签字 | 仓库温湿度、货位、入库/出库、留样柜温度 | 全套放行项目、稳定性/保质期支持、法规特定项目 | 成品批 → 放行样品/报告 → 质量决定 → 库存单元 |
| 11. 仓储 | 温度/湿度、光照、货位、先进先出、异常时长、开门/断电 | 连续温湿度、光照、门磁、电源、冷库/仓位 ID | 异常后的复检、稳定性和氧化趋势 | 成品批 → 库位 → 温度设备 → 异常事件 → 处置记录 |
| 12. 运输与交接 | 运单、车辆/箱码、承运商、起运/到达、封签、温度异常、货损 | 温度/湿度、GPS、门磁、冲击、光照、断电、交接扫描 | 超温/货损后的复检、必要时独立抽检 | 成品批/箱码 → 运单 → 车辆/容器 → 交接事件 → 签收 |
| 13. 交付与消费者反馈 | 收货时间、包装状态、批号可查、气味/口感反馈、储存条件、退货/投诉 | 交付扫描、签收、消费者授权设备的时间和位置（最小化） | 争议复检、投诉样品、召回确认 | 箱码/单盒码 → 订单/购买证明 → 消费者授权 → 反馈事件 |

### 5.1 样品、设备和批次的绑定规则

建议形成以下有向图，而不是只存一张批次表：

    原料批次
      ├─ 取样事件 → 样品 → 样品封签/交接 → 实验室报告
      ├─ 投料事件 → 工单 → 设备运行段 → 中间体批次
      └─ 供应/收货记录 → 运输单元 → 到厂验收

    中间体批次
      ├─ 浓缩/脱臭/混合工艺段
      └─ 灌装工单 → 半成品批 → 包装批 → 成品批

    成品批
      ├─ 放行报告/留样
      ├─ 库位与温度时间线
      ├─ 运单/车辆/容器/交接
      └─ 订单/箱码/消费者反馈

每条边都应有 relationType、validFrom、validTo、createdBy、evidenceRef 和可撤销状态。批次合并、拆分、返工和重包装必须是显式事件；禁止通过覆盖旧批号来“修正”关系。

## 6. EvidenceEnvelope、批次图和哈希边界

### 6.1 EvidenceEnvelope 建议字段

    {
      "envelopeVersion": "evidence-envelope-v1",
      "eventId": "evt-01H...",
      "eventType": "lab_report | production_step | cold_chain_reading | disclosure_event",

### 6.2 规范化和证据根

哈希前必须做固定的规范化：

- 时间统一为带时区的 ISO 8601；
- 数值保存原始单位和规范单位，禁止隐式换算；
- 字段顺序、空值规则和 Unicode 规范固定；
- 原文、规范化摘要、签名和版本分别可回查；
- 同一事件有稳定的 eventId 和幂等键；
- 批次的一组证据用排序后的 eventId + payloadHash 形成 evidenceRoot。

当前仓库基于 JSON.stringify 的哈希只适合 Demo，生产版需使用明确的规范化 JSON/CBOR 规则和版本化算法。

### 6.3 链下保存什么

链下保存：

- 原始 PDF、谱图、设备明细、温度时间序列和图片；
- 个人信息、订单全文、供应商商业信息和受限数值；
- 校准证书、维护记录、实验室资质和样品交接附件；
- 访问日志、授权记录、撤回记录和争议材料。

链下证据仓需要访问控制、不可篡改版本、备份、保留期限和删除/撤回策略。删除原文后仍应保留“原文已不可访问/已按策略销毁”的审计事件。

### 6.4 BOT Chain 锚定什么

链上只保存最小公共承诺：

- batchId 或其隐私保护标识；
- issuerId、设备/实验室主体 ID；
- payloadHash、schemaHash、evidenceRoot；
- 观察时间、提交时间、前一事件哈希；
- taskHash、policyHash、verifierVersion；
- jevSchemaHash、模型版本哈希和路由代码；
- resultStatus、resultScope、缺口/冲突代码；
- 撤销、争议、替代记录和幂等键。

链上不保存报告全文、原始 prompt、个人信息、秘密密钥、健康信息或需要保密的精确数值。锚定失败时链下验收结果仍保留并标记 anchor_pending 或 anchor_failed；不能为了重试而生成第二个不同事件。

## 8. 哪些检查可以由 Agent + JEV + 规则重塑

适合重塑的领域：

- 将自然语言采购问题映射为 requestedChecks 和声明范围；
- 统一 ERP、MES、LIMS、物流和设备导出字段；
- 做批次/样品/设备/报告的关系核对；
- 做重复、过期、缺失、时间回拨和跨系统冲突检测；
- 根据缺口路由到实验室、物流服务或厂家补证；
- 计算固定阈值、规则组合、证据范围和结果状态；
- 生成面向消费者、厂家、评委或审计人的不同解释；
- 维护可回放的证据根、规则哈希和信誉反馈。

仍必须由实验室、法规或人工复核决定的领域：

- EPA/DHA、氧化、污染物、微生物等现实样品的测量；
- 检测方法的适用性、方法验证、不确定度和实验室资质；
- 取样代表性、样品封存、运输和交接是否足以支持结论；
- 设备校准、安装位置、替换和异常维护的实物确认；
- 产品是否符合法规、标签声明、进口/出口要求或召回条件；
- 设备被篡改、样品被调包、串通或责任归属的争议判断；
- 医疗、营养、功效和安全承诺；
- 放行、隔离、召回、销毁、赔付等有法律或运营后果的决定。

Agent 可以把人工任务排好优先级并准备证据包，但不能以语言流畅度替代这些责任主体。

## 9. 风险、信任边界和数据治理

| 风险 | 可能后果 | 首要控制 | 责任边界 |
| --- | --- | --- | --- |
| 厂商自报错误/造假 | 形成过高信任 | 来源分级、独立实验室、抽检和争议 | 厂商承担声明责任，TruthPass 只证明提交和规则范围 |
| 批次或样品错配 | 把别的结果套到当前货 | 强制关系边、序列/封签、重复和错配规则 | 网关与质量负责人共同维护批次图 |
| 设备替换/校准过期 | 温度或工艺数据失真 | 设备身份、证书、校准、维护、时钟和异常规则 | 设备持有人负责设备状态 |
| 实验室方法/资质不适用 | 结果不可用于目标结论 | 方法版本、单位、资质和范围校验 | 实验室负责报告专业责任 |
| Agent/JEV 选择性披露 | 隐藏负面或未覆盖项目 | failed/missing/restricted/not_covered 强制显示 | 产品与平台负责呈现完整状态 |
| 规则或标准漂移 | 新旧结果不可比 | policy hash、生效时间、版本回放 | 规则所有者负责变更审批 |
| 模型越权/幻觉 | 错误路由或解释 | 固定枚举、失败关闭、Verifier 接管 | 模型供应方不承担最终验收 |
| 隐私/商业机密泄露 | 合同和个人风险 | 最小授权、链下访问控制、链上哈希 | 数据控制者负责合法性和保留 |
| 链/RPC/对象存储故障 | 记录不可及时回放 | 链下先落库、重试幂等、备份和离线证据卡 | 运营方负责可用性和恢复 |
| 激励冲突/刷信誉 | 公共评分失真 | 购买/任务绑定、身份关联、时间衰减、独立复检 | 平台负责反作弊与披露付款关系 |

信任应按四层理解：

1. 来源信任：谁产生或转交了记录；
2. 内容完整性：记录提交后是否被改写；
3. 测量和过程可信：设备、样品、方法和环境是否足够可靠；
4. 结论适用性：该证据是否足以回答当前问题。

哈希主要覆盖第二层，签名和主体注册覆盖第一层的一部分，实验室、设备治理和人工复核决定第三层，规则和声明范围决定第四层。不能把一层的证明扩写成四层全部成立。

## 10. 实施优先级与退出条件

### P0 现在可做

- 冻结 EvidenceEnvelope、批次图和状态枚举；
- 为现有 demo/synthetic 数据增加来源、范围、缺口和冲突展示；
- 将 Agent/JEV/Verifier 的输入输出契约写成固定 JSON；
- 把报告全文、设备明细、哈希和链上目标网络明确区分；
- 为规则模板增加单位、方法、标准/产品规格引用和版本字段；
- 演练错批次、离线、签名失败、缺失字段和负面证据不可隐藏。

退出条件：评委可在一次演示中看懂“哪些已验证、哪些只是声明、哪些没有覆盖”，并能用同一输入回放相同结果。

### P1 试点前必须做

- 建立 ERP/MES/LIMS/WMS/TMS/设备的只读适配器；
- 生成真实 EvidenceEnvelope，验证签名、公钥、密钥状态和重复；
- 真实批次、样品、设备、工单和报告关系可回放；
- 接入至少一个独立实验室和一个温度记录源；
- 完成最小披露矩阵、访问日志、保留周期和争议流程；
- 链下证据仓和 BOT Chain 锚定具备幂等、失败重试和回查能力。

退出条件：至少一个真实批次从收货到交付完成证据图；出现任何关键冲突时结果自动进入复检/人工处理，而不是被 Agent 解释成通过。

### P2 规模化前必须做

- 多工厂、多实验室、多物流主体和多版本规则并行；
- 密钥轮换、设备吊销、校准/维护周期、时钟同步和离线缓冲；
- 复检、申诉、冻结、替代、召回和赔付的责任合同；
- 规则变更审批、模型版本登记、JEV 评测集和回放审计；
- 供应商付款关系、信誉操纵和利益冲突披露；
- 对象存储灾备、删除/撤回处理、长期可读性和安全审计。

退出条件：系统能给出“当前结论、适用范围、完整证据链、反例、责任方和下一步”，并能在模型、链或单个数据源故障时安全降级。

## 11. 与当前 v0.5.1 仓库实现的关系

当前仓库已经有服务探测、执行验收、消费者授权/购买/反馈的内存级 Demo；鱼油数据和错误服务是合成演示，signatureValid 仍是布尔输入，JEV adapter、真实设备签名验证、EvidenceEnvelope 运行时、BOT Chain 部署和公共锚定尚未由现有代码证明。

因此本文中的 P1/P2、设备接入、实验室治理、链上字段和争议机制均是实施建议。它们不能被写成“已经接入 ERP/MES/LIMS”“已经完成真实实验室认证”或“已把鱼油数据上链”。对外仍应沿用审计结论：当前完成的是可演示的服务可用性探测、本次交付确定性验收和消费者反馈模型；生产级真实性、公共锚定和争议责任需要后续交付与现场证据。
