## 1. 结论先行

当前仓库已经具备一个可以现场演示的最小闭环：

```text
候选服务登记
  → 当前可用性探测
  → 本次交付执行
  → 确定性验收
  → 服务排序
  → 本地履约反馈
  → 消费者授权 / 购买绑定 / 一次性反馈
```

`npm test` 通过 4 项，`npm run typecheck` 通过，`npm run demo` 能选出 `lab-c` 并生成鱼油批次反馈。因此，仓库可以支持“Agent 如何选择当下更可靠的服务”的黑客松演示。

但当前实现还不能证明以下更强的命题：

- 现实生产线、检测设备和物流设备的数据已经被密码学认证；
- 检测报告一定来自真实且独立的实验室；
- 证据已经真正写入 BOT Chain 并可从交易回放；
- JEV 已接入并对线上结果负责；
- 消费者购买证明和反馈已经具备抗伪造的链上身份。

所以当前正确的产品口径是：

> **真验 Demo 已实现“服务可用性探测 + 本次交付确定性验收 + 消费者反馈模型”；生产版的设备认证、链上锚定、角色权限和争议机制仍需补齐。**

## 3. 对问题一：怎样保证全流程一致，并让检测结果得到认证？

### 3.1 不能把“一定真实”交给某一个组件

区块链只能证明某个主体在某个时间提交过某个哈希；Agent 只能完成调用、关联和解释；物联网设备只能提供带签名的观察值。三者结合后，能保证的是：

1. 数据结构符合约定；
2. 数据绑定到明确的批次和事件；
3. 提交者身份可追溯；
4. 数据在提交后可发现被改写；
5. 验收过程可以按同一规则回放；
6. 争议和撤销可以追加记录。

它们不能单独保证设备没有被替换、采样没有被调包、实验室没有串通或生产方没有从源头提交错误数据。现实真实性必须由设备、实验室、批次交接、复检和争议机制共同承担。

### 3.2 生产版应采用的证据闭环

```text
原料 / 生产 / 检测 / 物流观察
          ↓
Edge Gateway 采集与签名验证
          ↓
EvidenceEnvelope 统一事件信封
          ↓
批次关联 + 交接关系 + 时间/序列检查
          ↓
JEV 只做结构化缺口识别和路由
          ↓
Deterministic Verifier 执行最终规则
          ↓
链下保存原文，链上锚定哈希和验收结果
          ↓
公共信誉与复检 / 撤销 / 争议
```

### 3.3 证据事件必须包含什么

每一条原料、生产、检测、物流和消费者事件都应至少包含：

```json
{
  "eventId": "evt-...",
  "eventType": "lab_report | production_step | cold_chain_reading",
  "subject": { "type": "batch", "id": "FO-2026-001" },
  "issuer": { "type": "device | lab | supplier | consumer", "id": "..." },
  "producedByAgent": "agent-id",
  "observedAt": "2026-10-06T10:20:00Z",
  "sequence": 1842,
  "previousEventHash": "0x...",
  "payloadHash": "0x...",
  "schemaVersion": "fish-oil-cold-chain-v1",
  "nonce": "...",
  "signature": "...",
  "attestationLevel": "device-signed | lab-signed | supplier-declared"
}
```

关键点是 `issuer`、`subject.batchId`、时间、序列、前一事件哈希和签名。Agent 只能把它们关联和解释，不能把“自报”改成“第三方证明”。

### 3.4 当前代码已经做到什么、没有做到什么

已做到：

- `src/verifier.ts:9-26` 检查任务 ID、批次 ID、报告时间、签名标志、物流中断和鱼油指标；
- `src/registry.ts:39-49` 先探测服务，再执行可用服务，并将当前可用性、本次验收和历史评分组合排序；
- `src/consumer.ts:44-79` 要求购买绑定后才能提交反馈，并限制同一购买记录只能反馈一次。

未做到：

- `ExecutionEvidence.signatureValid` 是调用方传入的布尔值，未验证签名、公钥、密钥状态或签名内容；
- 没有 `EvidenceEnvelope`、设备序列、前一事件哈希、nonce、校准记录和吊销状态的运行时代码；
- 没有检测“同一个报告被复制到多个批次”或“设备时间回拨”的逻辑；
- `reportTime >= productionTime` 是字符串比较，生产版需要统一时间格式和时间源策略；
- 当前验收哈希基于 `JSON.stringify`，生产版必须使用固定字段顺序或规范化 JSON，避免同一事实因字段顺序不同得到不同哈希；
- 当前 `TaskRequest` 的鱼油阈值没有同时绑定检测方法、单位、标准版本和实验室资质。

### 3.5 “认证”应该如何对外表达

建议输出三层状态，而不是一个绝对的“真/假”：

- `accepted`：声明范围内的必需证据齐全，规则全部通过；
- `accepted_with_scope`：当前声明范围内通过，但仍有未覆盖字段；
- `review / rejected`：缺证据、冲突、签名失败、批次错配或规则不通过。

页面和 Agent 都必须显示：证据来源、规则版本、缺口、数据类别和链上锚定状态。不能把“链上有记录”翻译成“现实世界一定真实”。

## 4. 对问题二：鱼油 Demo 厂家一开始需要付出什么？

### 4.1 比赛 Demo 不需要改造整条产线

比赛版本可以使用 `demo/synthetic` 的批次、实验室报告摘要和冷链事件，重点演示数据模型、服务探测、验收和公共记录。此阶段厂家不需要购买硬件，也不需要把生产系统全部改造成智能工厂。

厂家只需要提供一套明确的批次样本：

- 批次 ID、生产时间和产品规格；
- 原料或原料批次的引用；
- 第三方检测报告摘要；
- 运输或仓储温度摘要；
- 生产方声明与实际检测结果的来源标签；
- 允许公开的证据字段和保密字段边界。

### 4.2 试点阶段也不要求推倒重来

最经济的路径不是替换所有设备，而是接入已有设备的导出能力：

```text
已有检测设备 / 温度记录器
          ↓ CSV / JSON / HTTPS / MQTT
Edge Gateway / 厂内适配器
          ↓ 签名、批次绑定、序列检查
TruthPass Evidence API
          ↓
JEV + Deterministic Verifier + Chain Adapter
```

厂家需要投入的主要是：

1. 设备或实验室系统的接口适配；
2. 批次和样品编号的一致编码；
3. 设备密钥、实验室签名和权限管理；
4. 校准证书、维护记录和异常处理流程；
5. 允许哪些证据公开、哪些只做哈希锚定的治理规则。

### 4.3 Agent 不能成为“挑数据的中间人”

你提出的“检测设备数据直接和 Agent 打通，由 Agent 有选择地提供”需要改成：

> **Agent 可以按消费者问题做最小化披露，但不能拥有删掉不利证据的权限。**

正确的分工是：

- 设备或实验室把完整事件提交给证据网关；
- 证据网关保存原始记录、哈希和签名；
- Agent 读取经过权限控制的摘要；
- 选择性披露只决定消费者看到哪些字段；
- 被隐藏的关键字段必须以 `missing / restricted / not covered` 显示；
- 任何“拒绝提供”也要形成事件，不能静默消失。

这样既保护商业和个人隐私，也避免 Agent 只挑好看的数据。

### 4.4 检测报告是否需要上链？

需要上链的是**报告的可验证承诺**，不是报告全文：

链下保存：

- 原始 PDF、图片、谱图和设备明细；
- 个人信息、实验室内部信息和商业配方；
- 需要权限才能查看的完整数据。

链上保存：

- `batchId`；
- `reportId` 和报告哈希；
- 实验室或设备主体 ID；
- schema / 检测方法 / 规则版本哈希；
- 观察时间、提交时间和前一事件哈希；
- 验收结果、证据根哈希、撤销或争议状态。

因此答案是：**报告需要锚定，不需要把原文全部公开上链。** 若报告更新，不能覆盖旧记录，应追加新版本和撤销/替代关系。

## 5. 对问题三：架构里到底有几条链？

### 5.1 当前不是多链架构

根据当前仓库，实际设计应理解为：

```text
一条公共链：BOT Chain（文档目标网络，Chain ID 677）
          │
          ├── 身份登记逻辑层
          ├── 证据哈希锚定逻辑层
          ├── 验收结果逻辑层
          ├── 公共信誉逻辑层
          └── 消费者共建权益逻辑层

链下：数据库 / 对象存储 / 向量检索 / IoT 网关 / 原始报告
```

“五层”是同一条公共链上的业务逻辑分层，不是五条区块链。当前没有第二条生产私链、检测链、Agent 链或跨链桥实现。

### 5.2 当前合约实际覆盖范围

`contracts/TrustRegistry.sol` 当前只有一个合约，包含：

- 服务注册；
- 服务反馈；
- 反馈撤销；
- 消费者购买记录；
- 消费者贡献事件。

它还没有实现文档中规划的：

- 主体 / 设备 / Agent 公钥注册；
- `anchorEvidence`；
- `recordVerification`；
- policy hash / evidence root；
- 角色权限和独立仲裁；
- 批次状态机、密钥吊销和争议状态。

此外，仓库没有提供已部署合约地址、部署交易哈希或可回放的 BOT Chain 交易。因此“BOT Chain 已接入”目前只能说是目标网络和架构约束，不能作为已验证交付来宣称。

### 5.3 后续是否需要第二条链

比赛 Demo 不需要第二条链。若生产企业不愿把任何批次信息直接放到公共链，可以增加企业内部账本或权限链，但它只能作为链下/许可域的证据存储，最终仍需把公开可复核的摘要锚定到公共链。

不要为了“多链”而多链。当前最清晰的结构是：**企业/设备产生数据，链下保存原文，BOT Chain 保存公共承诺和履约结果。**

## 6. 当前审计发现

### P0：必须在对外宣称“认证”前解决

1. **签名没有被密码学验证**：`src/types.ts` 只有 `signatureValid: boolean`；`src/verifier.ts:12` 直接信任这个布尔值。
2. **公共合约缺少角色权限**：`TrustRegistry.sol:48-52` 允许任意地址注册服务；`54-75` 允许任意地址提交反馈；`85-106` 允许任意地址写入购买和贡献事件。
3. **没有证据和验收锚定函数**：当前合约没有 `anchorEvidence` 和 `recordVerification`，因此网页中的“链上锚定”尚未由仓库代码证明。
4. **消费者购买证明没有被验证**：合约只保存 `purchaseProofHash`，没有订单签名、网关授权、nonce 或重复证明校验。

### P1：试点前必须解决

1. 没有统一运行时 `EvidenceEnvelope` 和 `JevDecision` 类型。
2. JEV 仍是文档和网页静态演示，未见真实 adapter、超时、低置信度和回放实现。
3. `ServiceRegistry.evaluate` 会把被拒绝的服务也放入排序；生产路由必须明确“只能从可接受结果中选择”，否则全失败时可能误选最高分的拒绝项。
4. `recordFeedback` 只在内存中保存，缺少时间衰减、撤销读取、重复主体风控和多方复核。
5. 消费者授权没有撤销后的数据处理、签名确认和购买凭证来源校验。
6. 合约撤销权限只给服务 owner，缺少独立仲裁和证据冲突处理。
7. 测量值没有单位、检测方法、标准版本和实验室资质字段，不能直接形成真实质量认证。

### P2：规模化前解决

1. 设备密钥轮换、校准证书、时钟漂移和设备替换流程；
2. 链上 RPC 故障、Gas、确认数、幂等重试和离线回放；
3. 原始报告的对象存储、访问控制、保留周期和审计日志；
4. 抗女巫、抗刷分、利益冲突披露和复检市场；
5. 真实供应商、实验室和物流服务的 SLA 与争议合同。

## 8. 对外路演的准确说法

可以说：

> 真验把服务当前可用性、本次交付验收和消费者反馈连接起来；在生产版中，设备、实验室和物流事件会先形成签名证据，再由规则验收并将哈希锚定到 BOT Chain。

不应说：

- “区块链保证鱼油是真的”；
- “Agent 自动认证了现实世界”；
- “检测数据已经全部上链”；
- “JEV 消灭了所有幻觉”；
- “消费者购买后自动获得股权、分红或投资回报”。
