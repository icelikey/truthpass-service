# TruthPass 过程数据与 Agent 闭环

TruthPass 不把“数据”理解成一堆静态指标，而是把一件商品从生产到消费的可核验过程串起来。用户看到的最终回答只是过程链的一个投影。

## 三类数据

| 类型 | 例子 | 作用 |
| --- | --- | --- |
| 结果数据 | 检测报告、温度结果、购买 receipt | 说明发生了什么 |
| 过程数据 | 生产步骤、设备变化、检索命中、Verifier 判断、JEV 路由、用户确认 | 说明如何得出结论 |
| 评测数据 | 反馈、退货原因、缺口补充、企业改进结果 | 说明结果是否有用并驱动下一轮改进 |

## 采集入口

第一版采用低录入路径：

```text
手机扫码或拍照
→ OCR/二维码识别批次
→ Agent 补齐当前上下文
→ 生产系统、检测系统和 IoT 自动上报
→ 服务端生成证据包
→ Verifier 校验
→ JEV 决定补证、复核或继续
```

数据来源包括手机拍摄的标签和检测单、生产系统的工序记录、实验室报告、温湿度和定位设备、物流交接记录、外部钱包 receipt，以及用户在 Agent 中提交的反馈和售后结果。

## 证据边界

每条证据都必须绑定：

```text
tenantId
productId
batchId
evidenceId
issuerId
sourceKind
occurredAt
contentHash
signature
dataMode
```

服务端按以下顺序核对：

```text
字段结构
→ 租户、产品、批次绑定
→ 时间和单位归一化
→ 重复与冲突检查
→ 来源签名校验
→ 确定性规则验证
→ JEV 路由
```

原始报告、订单详情和个人信息留在链下。区块链只保存摘要、签名、业务事件和交易 receipt，用来证明某份记录在某个时间被某个身份提交或确认；它不直接证明商品质量、安全或疗效。

## Agent 的作用

Agent 只能读取当前 `tenantId/productId/batchId` 范围内的资料，解释 Verifier 和 JEV 已经得出的结果，并把缺口、冲突和下一步说清楚。Agent 不改变规则状态、不代替机构签名、不代替用户付款。

一次查询至少留下：

```text
traceId
inputEvidenceIds
citedEvidenceIds
Verifier 状态
JEV 决策
模型 Provider 和运行状态
validationStatus
```

这些过程记录可以帮助企业定位“哪一步缺资料、哪一种运输最容易出问题、用户为什么放弃购买”，从而把消费反馈回流到生产改进。

## 当前演示边界

`FO-2026-001` 当前仍是 `demo/synthetic`。持续变化的冷链和生产事件用于展示数据如何流动，不代表真实设备上报。只有真实生产方、检测机构、用户钱包签名和可回读的链上 receipt 全部存在时，才能进入真实认证或购买确认。
