# TruthPass 助农子项目 BP v0.1

## 一句话定位

**TruthPass 助农不是替农户做广告，而是把一件农产品从田间到餐桌的事实、检测、运输和购买反馈组织成一份可核验的商品记录，让消费者的选择反过来帮助生产者改进下一批产品。**

对外口号建议：

> 让每一份好农产，都有一条能被看懂、能被核对、能持续改进的记录。

## 1. 从访谈提炼出的真实问题

访谈反复指向四个矛盾：

1. 助农容易被简化成直播、电商和流量投放，质量投入反而不足；
2. 消费者想买放心农产，但看不到产地、生产、检测和运输的连续证据；
3. 生产者难以知道消费者收到货后的真实体验，无法把反馈稳定地变成下一批改进；
4. AI 可以降低解释和服务成本，但如果没有证据边界，也会放大错误推荐和食品安全风险。

TruthPass 的切入点是把“营销承诺”改成“可核验记录”，把“消费评价”改成“绑定购买批次的改进信号”。

## 2. 子项目边界

首个助农子项目使用现有 `rice-demo` 站点作为合成演示：

```text
站点：/sites/rice-demo
演示批次：RC-2026-001
状态：DEMO / SYNTHETIC
```

第一批正式试点只选：

```text
1 个生产主体
1 个明确品类（大米或地方特色农产）
1 个批次
1 家检测机构
1 条物流路径
20–50 个消费者样本
```

先做“一批可核验的农产”，再扩展成“放心农产目录”。不先做开放商城，不先做积分、代币或多级分销。

## 3. 核心闭环

```text
生产者登记批次
→ 上传/口述生产资料
→ Agent 整理成结构化证据
→ Verifier 按公开规则核对
→ JEV 决定补资料、复核或进入公开展示
→ 消费者扫码查看并向商品 Agent 提问
→ 消费者购买并取得购买凭证
→ 反馈绑定购买和批次
→ Agent 生成聚合问题与改进建议
→ 生产者确认改进任务
→ 下一批次对比改进结果
```

消费者 Agent 不替生产方认证，也不替检测机构签名；它只解释当前资料、指出缺口、显示来源和给出下一步。

## 4. 数据结构

### 4.1 生产资料

```text
tenantId / productId / batchId
growerId（生产主体）
plotIdHash（地块标识哈希）
seedSource（种源）
plantingWindow
fertilizerAndPesticideRecords
irrigationRecords
weatherAndSoilSnapshots
harvestQuantity
processingAndStorageRecords
```

### 4.2 检测资料

```text
sampleId
labId / issuerId
samplingTime
method
pesticideResiduePanel
heavyMetalPanel
moisture / mycotoxin 等适用品项
reportHash
issuerSignature
```

指标只按“实测值、检测方法、适用标准、报告来源”呈现。产品 Agent 可以说“该项在登记规则范围内”或“资料缺失”，不能把一次检测扩展成“绝对安全、治病或永久有效”。

### 4.3 物流和仓储

```text
shipmentId
warehouseIdHash
temperature / humidity
startAt / deliveredAt
interruptionDuration
sensorSource
```

### 4.4 消费和反馈

```text
purchaseId / purchaseTxHash
batchId / walletAddressHash
receivedAt
packageIntegrity
appearance / cooking / taste categories
transportIssue / returnReason
freeText（链下，默认不公开）
feedbackHash / contributionTxHash
```

公开层只展示聚合：样本量、分类计数、时间范围和趋势；原始评论、订单和个人信息留在受控存储中。

## 5. 核对机制

| 层 | 核对内容 | 结果 |
|---|---|---|
| 格式 | 字段完整、时间和单位合法、哈希格式正确 | 结构通过/拒绝 |
| 范围 | 数值与公开规则、检测方法和适用品项匹配 | 规则结果 |
| 关联 | `tenantId/productId/batchId/evidenceId` 不错配 | 绑定通过/拒绝 |
| 来源 | 生产者、实验室、物流设备的来源和签名状态 | 来源状态 |
| 一致性 | 产量、出货量、样品、订单和反馈数量可对账 | 对账结果 |
| 模型 | 只能引用白名单证据，不能新增指标和结论 | accepted/fallback/rejected |
| 人工责任 | 生产方和检测/审核机构确认待签操作 | 责任记录 |

## 6. 区块链在助农项目中的位置

链上保存适合公开核验的摘要，而不是把原始农田资料和个人信息全部上链：

```text
证据内容哈希
证据根或批次摘要
签发者地址/角色
规则版本
序号和时间
购买/反馈事件摘要
真实交易 receipt
```

区块链能证明“某个摘要、签名、事件在某时刻被某地址提交并可回读”，不能单独证明地块真的存在、检测机构一定没有错误，也不能把 `demo/synthetic` 变成真实认证。

## 7. Agent 分工

```text
生产 Agent：采集、整理、提示缺资料，不能自行把资料标成合格
检测 Agent：解释报告字段，不能替实验室签名
物流 Agent：接收设备和运输事件，不能篡改历史事件
消费者 Agent：回答“这批是什么、来源是什么、缺什么、我下一步做什么”
企业 Agent：汇总反馈并生成待确认改进任务
Verifier：确定性规则和对账
JEV：决定补证、复核、公开或拒绝
钱包：身份绑定和写操作确认
```

## 8. 对生产者的价值

1. 把质量投入转成消费者看得懂的商品记录；
2. 用一套模板减少向不同渠道重复报材料；
3. 看到按批次聚合的包装、物流、口感和退货问题；
4. 让下一批次的改进有前后对照，而不是靠宣传口号；
5. 在固定服务费或透明交易费下获得“证据驱动的直达销售”入口，避免竞价排名。

## 9. 对消费者的价值

1. 扫码即可看当前批次，而不是先看营销文案；
2. 可以问 Agent“依据是什么、缺什么、谁负责补”；
3. 看得到检测方法、来源、时间和链状态；
4. 反馈绑定购买凭证，进入生产改进，而不是沉在评论区；
5. 只读查询不要求钱包，写入购买和反馈时才需要外部钱包确认。

## 10. 激励设计：先做可控的参与奖励

访谈提出“完成打卡返现/共享数据价值”。助农首版不把奖励绑定“健康改善”或正面评价，避免虚假反馈、医疗暗示和合规风险。

建议第一版：

```text
真实购买
→ 完成一次结构化反馈
→ 获得下次购买优惠/运费券/试吃资格
```

后续若做现金返还，必须由真实购买、明确规则、预算上限和审计记录支撑；不能以好评换奖励，不能通过多级拉人获得收益。

## 11. 商业模式

### 试点阶段

```text
站点构建服务费
资料接入和检测对账服务费
按批次或订单收取透明技术服务费
```

### 规模阶段

```text
企业站点订阅
检测/物流连接器服务费
企业改进报告和审计导出
公开目录中的固定服务费
```

TruthPass 不以竞价排名决定曝光，不以“花钱就能改规则结果”为商业模式。

## 12. 90 天路线

### 0–2 周：可演示

```text
RC-2026-001 合成批次
生产/检测/仓储/运输证据卡
Agent 分阶段查询
缺口和冲突展示
生命周期滚动
```

### 3–6 周：单企业小试点

```text
签约 1 个生产主体
接入 1 家检测机构
接入 1 条物流路径
建立真实批次和人工确认流程
```

### 7–10 周：消费闭环

```text
真实消费者购买
购买凭证
反馈聚合
企业改进报告
下一批次对比
```

### 11–12 周：对外 BP 和复制

```text
发布试点数据报告
形成政府/园区/合作社版本方案
复制到第二个品类
```

## 13. 关键指标

```text
证据完整率：公开所需字段已登记的比例
来源可核验率：有来源和签名状态的证据比例
批次错配拦截率：目标 100%
模型越界拦截率：目标 100%
消费者查询完成率
购买后反馈率
反馈进入改进任务的比例
改进批次复测完成率
退货/物流问题下降趋势
```

不把 Agent 调用次数、曝光量和点赞量当成质量成功指标。

## 14. 风险和控制

| 风险 | 控制 |
|---|---|
| 资料造假 | 来源签名、抽样复核、现场/机构责任记录；链只固化摘要，不替来源背书 |
| Agent 幻觉 | Few-shot + 严格 JSON + 引用白名单 + fail-closed fallback |
| 食品/健康误导 | 禁止医疗诊断、疗效和绝对安全表述；功能性产品另设更高门槛 |
| 反馈刷量 | 只接受已核验购买凭证；一单一次；公开只做聚合 |
| 设备异常 | 标记缺失/冲突，不能自动解释为合格或不合格 |
| 生产方不改进 | 每项建议绑定责任人、截止时间和下一批次复核 |
| 政府合作误用 | 政府作为试点/监管协作方，不把平台展示写成政府认证 |
| 隐私泄露 | 原始评论、地块精确位置、订单和个人信息链下隔离 |

## 15. 试点合作门槛

合作方必须满足：

```text
愿意公开批次范围内的必要资料
接受第三方检测或抽查
愿意补缺口并处理争议
同意消费者反馈回到下一批次改进
不要求平台删除不利但真实的批次记录
```

“企业自己是否愿意把资料拿出来、是否愿意面对缺口”是第一筛选标准。
