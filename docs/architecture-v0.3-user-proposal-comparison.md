# TruthPass v0.3：用户方案与远程仓库架构对比

> 日期：2026-10-06
> 状态：架构统一稿

## 1. 统一定位

远程仓库解决的是：**Agent 如何选择陌生服务、验收交付，并把履约结果沉淀为公共信誉**。

用户方案补充的是：**商品/批次如何登记，生产、检测、物流和用户反馈如何结构化保存，由多个领域 Agent 协作判断，再为用户推荐风险调整后性价比更高的商品**。

统一定位：

> **TruthPass 是商品供应链中的服务可靠性与公共信誉层。商品批次是任务对象，供应商、检测机构、物流商和售后方是被探测、验收和评价的服务提供者。**

系统不宣称商品绝对真实，而是公开：谁声明了什么、哪些证据支持声明、哪些来源独立、哪些环节仍未验证，以及为什么推荐某个商品。

当前演示品类冻结为鱼油；茶叶和 Type-C 充电线保留为后续备选，不在同一条 Demo 流程中混用。

## 2. 两套方案的对照

| 领域 | 用户方案 | 远程仓库 | 统一结论 |
|---|---|---|---|
| 产品重点 | 商品生产白盒化、性价比推荐 | 服务探测、任务验收、公共信誉 | 用商品批次承载赛题一任务 |
| 商品/批次 | 商品和批次进入数据库 | 商品批次是任务载荷 | 保留 Product、Batch、Claim、Evidence |
| 证据 | 分类采集、清洗、JSON/YAML 格式化 | Evidence Normalizer | 使用版本化 Canonical JSON；YAML 只放规则和配置 |
| Agent | 生产、检测、用户反馈 Agent | Planner、Discovery、Probe、Evidence、Verifier、Router、Reputation | 一个 LangGraph 编排图，使用领域节点，不做自由对话 |
| 数据库 | Agent 不操作 SQL，代码层强约束 | 关系库保存事实，向量库辅助召回 | 使用 Supabase PostgreSQL，不维护 MySQL 双写 |
| 向量库 | Supabase / 向量检索 | 可选向量索引 | 只用于召回和解释检索，不用于判真 |
| 验收 | 生产、检测、反馈交叉验证 | 确定性 Verifier | 代码决定通过/部分验证/拒绝，Agent 发现冲突并解释 |
| 推荐 | 召回、粗排、精排、重排 | Router 选择服务 | 商品推荐增加推荐流水线，服务选择仍由 Router 完成 |
| 账本 | 用户主动反馈、防刷单 | 任务级 Feedback 和撤销 | 反馈绑定订单/任务哈希、服务身份和证据哈希 |
| 区块链 | 哈希比较、cursor、公共账本 | BOT Chain TrustRegistry | 现有链保存摘要和时间锚点，cursor 只做同步进度 |

## 4. 数据层方案

### 4.1 数据库边界

```text
Agent
  -> 受限工具
  -> Pydantic / JSON Schema 校验
  -> 业务服务与权限检查
  -> Supabase PostgreSQL
```

Agent 不直接访问数据库、不生成 SQL、不直接写链。代码层负责权限、字段校验、分类、状态、幂等和写入。

核心表：

```text
organizations         厂商、检测机构、物流方、平台
services              可调用服务和能力声明
products              商品
batches               商品批次
claims                厂家声明
evidence              证据元数据和规范化 JSON
verification_tasks    验收任务
verification_results  验收结果
feedback              用户和 Agent 反馈
ledger_events         追加式账本事件
outbox                待上链事件和同步 cursor
```

原始 PDF、图片、视频和报告文件存入 Supabase Storage；数据库保存 URI、类型、哈希、来源、权限和状态。pgvector 仅用于自然语言召回和解释检索。

### 4.2 证据分类

首版固定证据类型，禁止 Agent 自由发明：

```text
material_lot       原料批次
production_event   生产事件
inspection_report  检测报告
shipment_event     出厂/物流事件
purchase_record    购买记录
user_feedback      用户反馈
```

统一证据信封至少包含：`schema_version`、`evidence_id`、`batch_id`、`kind`、`issuer_id`、`source_kind`、`payload_uri`、`payload_hash`、`verification_level` 和 `status`。

### 4.3 单一事实源

Agent 之间只传版本化 Canonical JSON：

```text
Canonical JSON
  -> 生产 Agent 输入
  -> 检测 Agent 输入
  -> 反馈 Agent 输入
  -> 用户证据卡
  -> Markdown 报告
  -> 链上摘要
```

JSON 用于运行时通信；YAML 用于标准、规则、Prompt 和测试样例；Markdown 用于用户报告；SQL 只存在 migration 和业务代码中。

## 5. Agent 协作方案

### 5.1 目标采用单图编排，不采用自由多 Agent 对话

目标使用一个状态图；当前 TypeScript MVP 先用普通 async orchestrator，只有出现状态持久化、人工中断或复杂分支恢复需求时再引入 LangGraph：

```text
Planner
  -> Discovery
  -> Probe
  -> Evidence Normalize
  -> Production Assessment
  -> Inspection Assessment
  -> Feedback Assessment
  -> Deterministic Verification
  -> Challenge
  -> Risk / Reputation
  -> Recommendation
```

领域 Agent 可以有不同 Prompt，但必须共享相同的 Schema、证据 ID、只读工具权限和“不得编造数字/哈希/机构/结论”的约束。

### 5.2 三个领域 Agent

- **生产 Agent**：检查原料批次、生产事件、数量、时间、地点和厂家声明，输出批次关联、生产完整性和缺失证据。
- **检测 Agent**：检查检测机构、报告号、样品号、批次绑定、标准版本、指标和有效期；数值比较由规则引擎完成。
- **用户反馈 Agent**：只分析绑定订单的反馈，识别重复评价、异常集中、批次不一致和常见问题，不直接修改信誉分。
- **挑战节点**：寻找错批次、过期报告、非独立来源、单位错误和证据断链，不能直接改写规则结果。

Agent 输出是候选判断，最终 `pass / partial / reject` 由确定性代码计算。

## 6. 真实性和交叉验证

不能仅凭厂家上传的数据 100% 判断现实世界真假。系统必须区分：

```text
self_asserted          厂家自报
schema_valid            结构合法
hash_anchored           内容已锚定且未被替换
issuer_verified         签发方身份可验证
cross_consistent        与其他记录一致
independently_tested    独立机构检测
physically_attested     抽检、封签或可信设备证明
```

推荐交叉验证链：

```text
原料批次 -> 生产批次 -> 检测样品号 -> 包装/出厂批次 -> 物流 -> 购买订单
```

结论只能是“在当前证据范围内通过、部分验证或拒绝”，不能输出 `is_true=true`。标准符合性只证明检测值符合标准，哈希只证明内容未被替换。

## 7. 风险、信誉与防刷

### 7.1 硬门槛

关键安全检测缺失、指标超标、报告无法关联批次、签发方无法验证、证据严重过期/撤销或批次关键节点断裂时，不得被低价或历史高分抵消。

### 7.2 软风险

```text
risk_score =
  证据缺失   30%
  批次断链   25%
  来源冲突   20%
  签发方风险 15%
  反馈异常   10%
```

风险分由代码计算；Agent 只能提出检查项和解释原因。

反馈必须绑定：

```text
order_id + batch_id + service_id + task_hash + evidence_hash
```

同一订单只能评价一次；修改、撤销、争议和复核均追加新账本事件，不覆盖旧记录。

## 8. 商品推荐链路

```text
用户需求解析
  -> 硬约束过滤
  -> 召回
  -> 粗排
  -> 精排
  -> 重排
  -> 证据化解释
```

- 硬约束：排除关键证据缺失、严重风险、批次无法识别和检测失败商品。
- 召回：PostgreSQL 条件查询、用户偏好和可选 pgvector 语义搜索。
- 粗排：证据完整性、验收状态、风险和价格。
- 精排：预算、风险偏好、质量、履约、反馈和价格。
- 重排：处理同品牌重复、价格区间和风险曝光。

向量库只负责找候选，不负责判真；推荐结果必须展示支持证据、未验证项、风险和价格取舍。

## 9. 区块链、哈希和 cursor

数据库保存结构化事实，Storage 保存原始文件，代码对规范化 JSON 计算哈希；区块链保存批次摘要、服务身份、证据哈希、验收结果、报告哈希、版本、提交者和时间锚点。

`cursor` 只用于 outbox 增量同步：

```text
扫描未存证事件 -> 提交交易 -> 保存 tx_hash -> 推进 cursor
```

cursor 不是信任证明；哈希证明内容未被替换；多来源验收才支撑事实可信程度。

## 10. 与远程仓库现有代码的关系

以下基础可以直接保留：

- `src/types.ts`：公共任务、证据和反馈类型；
- `src/registry.ts`：服务注册、探测和推荐；
- `src/verifier.ts`：确定性证据验收；
- `src/hash.ts`：报告/证据哈希；
- `contracts/TrustRegistry.sol`：最小公共信誉登记合约；
- `test/verifier.test.ts`：批次匹配与签名验收测试。

下一阶段增量扩展：

1. 增加鱼油批次字段、`schema_version` 和证据类型。
2. 增加生产、检测、用户反馈三类 assessment。
3. 增加硬拦截、推荐分和反馈防刷规则。
4. 再接数据库、Storage、LangGraph 和 outbox。

## 11. 必须冻结的决策

1. Demo 品类冻结为鱼油；茶叶和 Type-C 不混入本次演示。
2. 数据库使用 Supabase PostgreSQL，不维护 MySQL 双写。
3. JEV 必须定义为明确的 Schema/语义词汇，不作为模糊模型名。
4. Agent 不做自由多 Agent 对话；当前 MVP 使用 TypeScript async orchestrator，后续有状态持久化需求再引入单一 LangGraph。
5. 所有演示数据标记 `demo/synthetic`。
6. 区块链只做公共锚定，不替代数据库、对象存储或验收器。

## 12. MVP 验收标准

- 两个鱼油候选商品，各有一个可查询批次。
- 每批有原料、生产、检测、出厂/物流和购买反馈数据。
- 至少一个服务当前可用、一个服务离线、一个服务返回错批次报告。
- 三类 Agent 输出合法 JSON，且只能引用已有证据 ID。
- 确定性验收器输出通过、部分验证或拒绝。
- 关键检测缺失或批次不匹配时硬拦截。
- 推荐链路完成硬过滤、召回、粗排、精排、重排和解释。
- 反馈绑定任务/订单并可识别重复或撤销。
- 报告哈希可重复计算，链上只保存摘要。
- 现有测试和类型检查持续通过。


## 13. 架构评优

### 13.1 评价维度

| 维度 | 用户原始方案 | 远程鱼油方案 | 评价 |
|---|---:|---:|---|
| 赛题一契合度 | 7/10 | 10/10 | 远程方案直接围绕服务探测、履约验收和公共信誉展开 |
| 业务完整性 | 9/10 | 8/10 | 用户方案覆盖数据库、证据、反馈和推荐更完整 |
| MVP 可落地性 | 5/10 | 9/10 | 用户方案若全部实现容易超范围；远程方案已有代码、测试和 Demo |
| 证据可信边界 | 7/10 | 9/10 | 远程方案明确区分服务可用、交付验收和现实真实性 |
| Agent 可控性 | 6/10 | 9/10 | 远程方案把关键判断留给确定性 Verifier |
| 演示叙事 | 7/10 | 10/10 | 鱼油指标、离线服务、错批次和消费者反馈形成完整现场故事 |
| 扩展性 | 9/10 | 8/10 | 用户方案的领域服务拆分更完整，但需要后续逐步落地 |

### 13.2 优选结果

**第一名：远程鱼油 TruthPass 架构。**

它应作为系统骨架，因为已经具备：

- 赛题一核心闭环；
- 服务注册、探测、验收和信誉聚合；
- 鱼油领域指标；
- 消费者授权与反馈；
- 确定性规则和测试；
- 链上存证边界。

**第二名：用户提出的分层架构。**

它不应被舍弃，而应作为远程架构的内部设计约束，尤其保留：

- Agent 不直接操作 SQL；
- 数据按证据类型强约束；
- Canonical JSON 作为 Agent 间唯一事实格式；
- 生产、检测、反馈的领域节点；
- 召回、粗排、精排、重排的推荐层；
- 反馈账本和防刷机制。

### 13.3 最终推荐架构

```text
远程 TruthPass 服务验收骨架
  + 用户方案的数据治理和业务分层
  + 鱼油领域确定性指标
  + 单一状态编排图（MVP 为 TypeScript async orchestrator）
  + Supabase PostgreSQL / Storage
  + EVM 最小公共存证
```

### 13.4 必须删减的内容

首版不同时实现：

- 多个独立部署的 Agent 服务；
- MySQL 与 PostgreSQL 双写；
- 复杂向量推荐；
- 完整商城和支付；
- 真实 IoT 接入；
- 代币、分润和复杂 DAO；
- 让 LLM 直接决定验收分数。

### 13.5 实施优先级

```text
P0 服务探测 -> 鱼油任务验收 -> 错批次/离线/成功三种结果
P1 消费者授权购买 -> 反馈防重复 -> 公共信誉更新
P2 数据库/Storage 适配 -> async orchestrator -> 链上锚定
P3 召回/粗排/精排/重排和更丰富的商品推荐
```

最终原则：**先证明一次服务履约结果可信，再用这个结果帮助下一个 Agent；商品推荐是上层体验，不应抢走服务验收这个赛题核心。**

## 14. 整体复盘：需要优化的边界

### P0：检测服务履约与鱼油质量判定必须拆开

当前 `verifyExecution` 同时检查服务签名/批次/报告时间，也检查 EPA+DHA、过氧化值、TOTOX 和冷链指标，并把所有失败归为服务 `rejected`。这会造成错误归因：实验室正确检测出鱼油不合格，可能是“服务完成了任务，但商品批次不合格”，不应被记成实验室履约失败。

拆为两个独立结果：

```text
ServiceExecutionResult：服务是否按约交付有效、可验证的报告
ProductBatchAssessment：报告中的商品指标是否满足版本化验收规则
```

服务履约只检查任务/批次对应、报告格式、签名、交付时间、能力匹配和证据完整性。商品评估才检查 EPA+DHA、氧化指标、冷链等产品条件。信誉聚合使用前者；商品推荐使用后者。

### P0：验收阈值不能由请求方任意下发

当前任务对象携带 acceptance 门槛。若调用 Agent 可自行降低阈值，就能把不合格产品请求成“合格”。阈值必须引用受控 `policy_id + version + source`，由代码加载并校验适用品类、指标、单位和方法；调用者只能提出偏好，不能覆盖强制标准。具体阈值应由团队依据适用标准确认后配置，不在代码中无来源硬编码。

### P0：探测/路由资格与排序分离

离线、能力不匹配、Schema 错误、签名无效或本次硬失败的服务不得进入可选推荐集。当前 registry 对所有候选计算加权分后排序，且历史分可以给未执行或失败候选留分。改成两阶段：

1. 资格过滤：在线、能力匹配、协议/schema 合法；本次执行完成后还必须通过服务履约门槛。
2. 仅对合格候选按经验证的近期履约、延迟和成本排序。

无合格服务时明确返回 `no_eligible_service`，不能挑一个最高分失败者。

### P0：证据签名必须由代码验证，不信任布尔字段

`ExecutionEvidence.signatureValid` 是 adapter 直接提供的布尔值，不能作为线上信任边界。真实验收器必须接收签名和签名 payload，由代码使用已登记的服务公钥验证；同时检查签名者是否就是被调用服务、密钥是否有效/撤销、签名是否绑定 taskId、batchId、报告哈希和时间。Demo 的布尔值只能标为模拟输入。

### P0：消费者授权、购买凭证和反馈权重分层

当前内存实现只检查“存在任意授权”，没有按 feedback category 校验 scopes；购买凭证只是字符串哈希，也没有真实验证购买来源。链上购买和贡献方法也没有证明调用者拥有对应消费者身份/购买凭证，贡献 ID 未持久化防重。

边界调整：

- `purchase` 授权与 `quality-feedback`、`odor` 等反馈范围分开校验；撤销后拒绝新读取/提交。
- 购买凭证由可信订单来源签发或由用户出示可验证凭证；未验证购买只作为低权重公开意见。
- 一次购买的反馈唯一性由数据库唯一约束和链上/链下幂等键共同保证，不能只靠内存扫描。
- 体验反馈不能冒充实验室检测；主观气味/包装反馈与客观质量指标分开聚合。

### P1：服务信誉、产品批次风险、消费者体验分开存储和展示

不要压成一个总分：

```text
服务信誉：实验室/冷链服务是否可靠履约
批次风险：FO-2026-001 证据和指标是否满足规则
消费者体验：已购买用户报告的主观体验及样本量
```

先执行安全硬门槛，再推荐批次；服务历史分只用于选择服务，不应直接增加或抵消商品质量分。显示样本量、时间范围、来源等级和不确定性。

### P1：链上合约只是公共登记，不是信誉裁判

当前合约允许调用者提交任意分数和 accepted 值，服务 owner 可以撤销该 service 的反馈；消费者购买登记没有验证购买凭证的签发者，贡献事件没有持久化唯一 ID。合约不能独立证明链下报告或购买真实。

部署前至少需要确定：谁有资格提交哪类记录、如何处理争议/撤销、记录是否允许服务方单方面撤销，以及贡献的唯一键。MVP 若来不及做完整权限体系，应明确把链定位为“提交事件的公开收据”，不将合约接受交易表述成链上认证或真伪背书。

### P1：当前代码与目标架构要标清“已实现/计划中”

仓库当前是 TypeScript + 内存 `Map` 的可运行核心，尚无 Supabase、向量库、API、LangGraph、真实签名验证和链上客户端。架构文档中这些属于目标设计，不能描述为已接入。

最小落地建议：保持 TypeScript，先用一个普通 async orchestrator 调用现有模块；当前没有需要图状态持久化、人工中断或复杂恢复的实现需求，不为使用 LangGraph 而引入 Python/第二运行时。若流程后续确实出现需要可视化状态、暂停恢复、多分支重试的需求，再评估 TypeScript LangGraph。数据库先只引入一个 PostgreSQL 持久层；pgvector 等召回能力等有真实检索需求再加。

### P2：推荐是上层，不进入当前核心闭环

当前代码的 `ServiceRegistry.evaluate` 是服务路由，不是商品召回/粗排/精排。MVP 先把服务资格过滤和服务选择做好，并输出通过验收的鱼油批次证据卡。商品级召回、粗排、精排应等商品候选数据、用户偏好和质量策略稳定后再建，避免混淆“选服务”和“选商品”。

## 15. 建议的责任边界总表

| 组件 | 输入 | 负责 | 不负责 |
|---|---|---|---|
| API/工具层 | Agent 请求 | 身份、权限、Schema、幂等、调用白名单 | 自由 SQL/任意链调用 |
| 数据层 | 合法结构化记录 | 持久化、版本、查询、原件引用 | 判断现实真伪 |
| Agent 节点 | Canonical JSON + 只读工具 | 规划、抽取、找冲突、解释 | 改库、定分、最终签发结论 |
| 服务验收器 | 任务约定 + 服务响应 | 服务交付是否合约定 | 商品是否安全/合格 |
| 商品规则引擎 | 批次证据 + 受控规则版本 | 指标比较、硬拦截、批次状态 | 证明初始提交事实绝对真实 |
| 信誉引擎 | 已验收的服务任务记录 | 服务近期履约聚合 | 用主观反馈改写检测结论 |
| 推荐器 | 合格批次 + 用户偏好 | 候选筛选、排序、解释 | 绕过安全硬门槛 |
| 区块链适配器 | 已规范化摘要 | 公开锚定、交易回执、重试 | 判定链下事实真假 |

## 16. 复盘结论

总体方向正确，但首版必须优先修复“服务履约 vs 商品合格”的概念混用、请求方可控阈值、失败候选仍参与排名、布尔签名信任和反馈授权/凭证不足这五个 P0 边界。其余数据库、LangGraph 和商品推荐能力按真实需求逐步接入，不因架构图出现就提前实现。
